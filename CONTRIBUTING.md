# 🚀 Contributing to Iconical

First of all, **thank you for considering contributing!** 💖

Iconical is an independent development and creative brand building software, games, plugins, developer tools, and open-source projects.

Whether you're fixing a bug, improving documentation, suggesting a feature, or submitting code, your time and effort are appreciated.

We welcome thoughtful contributions from developers of all experience levels.

Before getting started, please read our [Code of Conduct](https://github.com/imthatdev/.github/blob/master/CODE_OF_CONDUCT.md).

You can also review our full [Contribution Policy](https://iconical.dev/policies/contribution).

## Getting Started

Before contributing to a project:

1. Read the repository's README and available documentation.
2. Review its license and any project-specific contribution instructions.
3. Search existing issues and pull requests.
4. Check whether the project is actively maintained.
5. Follow its setup, coding, and testing requirements.

Each project may use different languages, frameworks, build tools, or development workflows.

**Repository-specific instructions take precedence over general guidance in this file.**

For larger changes, consider opening an issue or discussion before beginning implementation.

This helps avoid duplicated work and ensures the proposed change fits the project's direction.

## Reporting Bugs

Found something broken? Thanks for helping us find it! 🐛

Before submitting a bug report:

- Confirm you're using a supported or relevant version.
- Search existing issues for similar reports.
- Try to reproduce the problem consistently.
- Remove passwords, credentials, and personal information from logs.

A useful report should include:

- **Description:** What went wrong?
- **Version:** Which release or commit is affected?
- **Environment:** Operating system, engine, runtime, or other relevant details.
- **Steps to reproduce:** How can someone reproduce the issue?
- **Expected behavior:** What should happen?
- **Actual behavior:** What happened instead?
- **Evidence:** Screenshots, logs, or minimal examples, where helpful.

Use the repository's Bug Report template when available.

**Security vulnerabilities must be reported privately**, not through public issues. Please review our [Security Policy](https://github.com/imthatdev/.github/blob/master/SECURITY.md).

## Suggesting Features

Have an idea that could make a project better? We'd love to hear it. ✨

Before submitting a request:

- Check for similar suggestions.
- Explain the problem the feature would solve.
- Describe your proposed solution.
- Consider whether an existing feature already addresses the need.
- Include examples or mockups if they help clarify the idea.

Use the repository's Feature Request or Suggestion template where available.

Not every idea will be implemented, but thoughtful suggestions are always appreciated.

If you'd like to help build your suggested feature, mention that in your proposal.

## Creating Pull Requests

Ready to contribute code, documentation, or another improvement?

### Prepare Your Changes

1. Fork the repository or create a branch using an authorized workflow.
2. Set up the project according to its documentation.
3. Make focused changes that address the intended issue.
4. Follow the existing architecture and coding conventions.
5. Run the relevant tests or checks.
6. Update documentation when your changes affect user-facing behavior.
7. Submit a pull request against the appropriate target branch.

### Pull Request Guidelines

A good pull request should:

- Clearly describe what changed and why.
- Reference related issues when applicable.
- Keep unrelated changes separate.
- Explain any breaking changes or compatibility considerations.
- Include relevant tests or explain why tests are not applicable.
- Include screenshots or examples for relevant UI changes.
- Identify new dependencies and important licensing considerations.
- Avoid including secrets, credentials, or sensitive information.

For substantial architectural changes, please discuss the approach with maintainers before investing significant time.

### Code Quality

We encourage contributions that are:

- Readable and maintainable.
- Consistent with existing project conventions.
- Reasonably tested.
- Secure and mindful of user privacy.
- Appropriately documented.
- Compatible with the project's supported environments.

There is no universal coding style across all Iconical repositories.

For example, a TypeScript project, an Unreal Engine C++ plugin, and a documentation repository may use very different conventions.

Follow the standards established by the specific project instead of assuming one style applies everywhere.

## Testing Your Changes

Before submitting a pull request, run the checks relevant to the affected project.

Depending on the repository, this might include:

- Unit or integration tests.
- Build or compilation checks.
- Linting and formatting.
- Type checking.
- Manual functional testing.
- Compatibility checks.
- Documentation validation.

Refer to the project's README, package scripts, development documentation, or CI configuration for the correct commands.

If you cannot run a test, explain the reason in your pull request.

**Do not claim tests passed unless you actually ran them.**

## Documentation and Translations

Documentation fixes are valuable contributions too!

You can help by:

- Correcting outdated instructions.
- Improving examples and tutorials.
- Clarifying configuration or installation steps.
- Fixing broken links.
- Improving accessibility and readability.
- Translating supported content.

When translating, preserve technical meaning and avoid introducing unsupported claims.

Legal documents or licensing notices should not be substantially rewritten or translated without appropriate review.

## Dependencies and Third-Party Content

Before adding external packages, libraries, assets, or other materials:

- Check license compatibility.
- Review security and maintenance implications.
- Avoid unnecessary dependencies.
- Preserve required notices and attribution.
- Ensure you have the rights necessary to contribute the material.

Publicly available code is not automatically available for unrestricted copying or redistribution.

Please identify significant third-party dependencies or licensed material in your pull request.

## AI-Assisted Contributions

AI-assisted development tools may be used where permitted by the repository's guidelines.

However, contributors remain responsible for the code and content they submit.

Please verify generated changes for:

- Functional correctness.
- Security vulnerabilities.
- Compatibility with the project.
- Appropriate licensing.
- Accuracy of documentation and tests.

Where relevant, disclose substantial AI assistance that may affect the review of your contribution.

Generated output is not automatically safe, accurate, or free of licensing concerns.

## Licensing Contributions

Each repository is governed by its own applicable license.

Before contributing, review the project's `LICENSE` file and any component-specific notices.

By intentionally submitting material for inclusion in a project, you are expected to have the necessary rights to provide that contribution under the project's applicable licensing arrangements.

For repositories licensed under Apache License 2.0, Section 5 of that license governs intentional submissions unless you explicitly state otherwise or a separate agreement applies.

For other repositories, review the relevant license and contribution requirements.

**Contributing does not automatically transfer ownership of your original work to Iconical.**

If a project requires additional contribution permissions or a separate agreement, maintainers will identify those requirements.

### Branding and Assets

Iconical's trademarks and separately protected brand assets are not automatically licensed for unrestricted reuse merely because a repository contains open-source code.

Respect the applicable license and asset notices.

Do not represent unofficial forks or modified projects as official Iconical releases.

Existing permissions granted under valid open-source licenses remain unaffected.

## Review and Acceptance

Maintainers review contributions based on:

- Technical quality and maintainability.
- Security and compatibility.
- Project goals and scope.
- Documentation and testing.
- Licensing requirements.
- Available maintenance resources.

We may request changes, suggest another approach, postpone a proposal, or decline a contribution.

A pull request is not guaranteed to be merged, and the review process may take time.

Please keep discussions constructive and respectful.

## Community Standards

All contributors are expected to follow our [Code of Conduct](https://github.com/imthatdev/.github/blob/master/CODE_OF_CONDUCT.md).

We welcome respectful disagreement, constructive criticism, and questions from newcomers.

Harassment, threats, discriminatory abuse, and deliberate disruption are not permitted.

If you encounter inappropriate behavior, follow the private reporting instructions in the Code of Conduct.
